# Anima 与机器人大脑看板详细调研

这两个项目分别把社会交互能力落在居家陪伴和餐吧服务场景。Anima 已形成包含本地模型适配、感知、成员记忆、陪护规则和机器人输出协议的工程系统；机器人大脑看板已形成调用云端多模态模型、展示观察和服务建议、管理本地顾客档案的实验工具。两者有互补价值，但当前不是同一套系统，也不能仅靠合并目录就获得完整的机器人社会智能。

调研日期：2026 年 10 月 6 日。分析对象是本次完整 Git 克隆的默认分支代码。下面把源码可确认的行为、仓库作者的历史实验报告、这次复跑的结果和对你意图的推测分别标明。历史对话只用于判断项目方向，不作为代码能力或商业成绩的证明。

## 3 Anima 的版本演进

### 3.1 V2 社会交互分类与下一轮预测

`v2/social_world_zh/` 是原始工程核心，包含模型、标签、策略、状态转移、控制器适配和服务接口。底座是 Qwen3.5-2B 的文本主干，LoRA 与八个任务头共同训练。任务覆盖当前情绪、对话行为、意图、边界、策略、任务领域，以及下一轮情绪和对话行为。

V2 的 `imagine` 接口比较候选回应可能对应的下一轮状态分布，结合神经预测头和由 CPED 训练对话统计的条件转移先验。它的预测步长是 1，不是长期社会演化，也不是已识别因果效应的反事实模拟。

V2 README 自报：中文意图准确率 87.2%，当前 13 类情绪宏 F1 19.5%，下一轮情绪和对话行为宏 F1 分别 9.9% 和 7.8%。这些结果说明原始预测能力很弱，不能支撑自主社会规划。完整原始评测 JSON 没有随当前仓库提交，以上是仓库文档中的历史结果，本次未重新训练或复算。

V2 还提供持久边界、偏好、提醒和设备任务白名单。明确拒绝打扰优先于模型猜测；运动及 IoT 任务需要可信上游分别授权。`adapter.py` 提供带 UUID、时间戳及有效期的控制器请求，示例控制器是模拟器。

### 3.2 V4 转向当前理解与中文回应

V4 保留一个物理 Qwen 主干，通过任务路由切换三类适配器：原始任务、当前状态、中文对话。`social_v4/runtime_model.py` 的路由退出后恢复原适配器，避免分类和生成串扰；`predictor.py` 串行化模型访问。

`v4/models/release.json` 绑定底座 revision、状态适配器指纹、回复适配器 SHA256、接受的分类头及温度参数。当前接受 emotion、dialog_act、sentiment 三个状态头；意图、边界、策略和任务领域沿用 V2。

最重要的发布事实是 `future_prediction_enabled: false`。V4 `Predictor.imagine()` 明确返回禁用状态，V5 回应也标记 `forecast_enabled=False`。因此不能用 V2 的探索代码把当前 Anima 宣传成可推演未来的成熟社会世界模型。

V4 训练报告记录曾拒绝第一轮回复候选，理由包括无视觉时编造衣服外观、忘记已明确提供的物品位置；随后补充上下文纠正、缺失感知和只倾听场景进行修复训练。这体现了质量筛选，但报告叙述不能替代可交付的检查点和原始审查数据。

### 3.3 V5 当前主线

FastAPI 的当前版本号是 5.2.0。V5 在已有文本模型上加上本地视觉、语音、姿态、连续状态、加密记忆、沟通偏好和陪护服务。它复用 V4 和 V2 包，不是完全独立的第五版实现。

当前执行链路可以概括为：

```text
文字 / 摄像头 / 麦克风
  → 登录、许可与会话隔离
  → 视觉、身体、语音各自编码
  → HumanState 时序状态
  → 提醒、安全边界与原始任务策略
  → 记忆检索、沟通偏好、对话规划
  → 共享 Qwen 文本主干生成短回应
  → response_plan / 网页朗读 / 机器人输出包装
```

证据：`v5/social_v5/server.py`、`social_runtime.py`、`engine.py`、`predictor.py`、`human_state.py`、`temporal.py`。

### 4.2 文本模型

底座名义规模为 2B，项目固定为 Qwen/Qwen3.5-2B revision `15852e8c16360a2fea060d615a32b45270f8a8fc`。仓库作者的 V5.1 报告记录实际加载文本主干及适配器参数为 1,893,279,226。原下载底座中存在视觉权重不等于本项目实际使用了 Qwen 原生图像能力。

当前状态分类最多使用 256 tokens，生成与分类是分别调用的。V5 `predictor.py` 给生成设置最多 4096 tokens 上下文、128 个新增 tokens、最多两句；记忆文字预算 600 字符。V5 README 部分旧说明仍写 2048 tokens，当前应以代码为准。

这意味着 Anima 偏向短句、低成本的日常交流，不是长文研究助理。实际延迟仍受主干推理影响，不能仅用轻量感知模块的毫秒数声称整机实时。

CPU 共享底座 INT8 是实验路线。release 中记录 96 个探针里 CPU/GPU 情绪 top1 一致率 0.7292；它不是任务准确率，也说明 CPU 路线不能直接当作质量无损替代。

### 4.3 视觉与身份

YuNet 找人脸和五关键点；SFace 匹配本人同意登记的成员特征；EmotiEffNet-B0 提取八类表情。在升级链路中同级多任务 B0 提供八类分布、valence/arousal 和 1280 维特征，没有同时常驻两个完整表情模型。

balanced 和 best_edge 额外用 MediaPipe Face Landmarker 提供 478 点网格、52 个 blendshape、头部姿态与虹膜位置代理。blendshape 是面部动作系数，不是标准 FACS AU。代码把稳定动作转成“嘴角上扬”等可观察描述，不把一次微笑解释成心理健康结论。

视觉要求质量门槛、单人绑定和短时平滑；多人或与当前成员不符时，不把该人的状态强行绑定给登录者。视觉引用带 owner 与会话约束，短时帧有效期约 10 秒；HumanState 中更旧的视觉证据约 5 秒失效。

这条视觉路线没有通用物体检测与场景理解能力。问杯子颜色、桌上有什么，不应该期待它像千问 VLM 一样直接看懂。SFace 匹配也不替代 PIN 登录或活体认证。

### 4.4 身体线索

`body.py` 用 MediaPipe Pose Lite 的 33 点姿态，最多检测两个姿态，只有唯一可用身体时建立特征。输出肩部开放程度、躯干倾角、头低位置代理、整体和手部运动强度、姿态变化，以及图像尺度变化推测的靠近/远离。

身体几何不是经过训练的“身体情绪模型”。抱臂、坐立不安、重复动作等高层判断保留 unknown；图像尺度变化不是实际米制距离。多人身体不能自动判成说话者。

### 4.5 语音

ultra_light 使用 Whisper base INT8；balanced/best_edge 使用 SenseVoiceSmall INT8，经 sherpa-onnx 运行在 CPU。SenseVoice 一条链路同时提供 ASR、语言、情绪标签和声音事件。语音情绪概率、embedding 或连续 V/A 没有可用真实输出时不伪造。

DSP 提取音高、能量、停顿、活动比例及粗略语速。字符数除活动时间不等于标准语速测量；RMS 也不是物理声压级。

当前代码还接入 Silero VAD，语音活动接口接收 16kHz PCM16，语音识别接口接收 0.2–25 秒 WAV。前端默认停顿约 2 秒才结束一轮，单段最多 20 秒，有限分段和队列避免慢速说话截断或请求无限积压。TTS 使用微软在线 edge-tts 三种中文声音，也可选择本机设备声音。

V5 旧 README 仍有“Whisper、1.2 秒、无声音情绪、非全双工”等前阶段描述。当前源码增加 SenseVoice、2 秒停顿及依赖浏览器 AEC/VAD 的打断，因此应按版本看待这些冲突，不能把旧段落当成最新版事实。实际设备上的回声与打断体验仍需要验证。

“本地 AI”主要指识别、推理和存储。选择微软在线声音时，朗读文字会发往在线服务；使用本机声音才能避免这条 TTS 数据出网。在线声音许可由网页引导管理，不应误认为服务器接口本身实现了完整的逐次云端许可认证。

### 4.6 HumanState 与时序融合

HumanState 包含 face、voice、body、language、interaction、temporal 六部分，以及跨模态一致性、uncertainty、confidence 和 event。缺失值保持 None/unknown，不伪装成中性。

`temporal.py` 使用时间感知 EMA、有限历史、信号超时、置信门槛和事件逻辑；维护 10 秒与 30 秒趋势，并在本人许可下建立慢速个人基线。基线需足够样本和跨度，报告与代码要求至少 20 次观测和 120 秒跨度才参与输出。

用户明确自述优先，表情和声音不覆盖“我并不难过”。语言中的情绪线索有规则处理否定、引用、历史和他人描述；这些规则存在覆盖有限的问题，不能看成完美语义理解。

时序融合本身是零可训练参数的工程统计，不是新训练的多模态时序 Transformer。动作后的状态变化记录是关联，不是因果效果证明；schema 中存在字段也不代表已经有可靠感知来源。Big Five、信任、声纹分离等并未实现可用验证。

### 4.7 记忆

MemoryStore 以 SQLite 存储，每位成员隔离。成员 PIN 经带盐 scrypt 哈希；登录令牌有效一小时，私有接口用 `X-Member-Session`。服务器重新根据令牌和档案确定身份及许可，不信任请求 JSON 自称已经确认身份。

记忆分成工作上下文、事件、长期事实/偏好和会话摘要。事件只保存用户原话；摘要主要是摘录而非让模型编造总结。普通事件/摘要默认 30 天，物品位置自动事实默认 7 天，稳定事实可长期，手动 TTL 1–3650 天。

每人当前事实/偏好最多 500 条，事件/摘要最多 1000 条，旧版本最多 500 条。新事实替换旧版本，检索优先当前有效记录。混合检索使用 BGE-small-zh-v1.5、汉字二元组重合、新近程度、重要性和去重，最多选 5 条。

支持人工添加、纠正、逐条删除、全部遗忘、撤回许可和删除成员。自动提取偏好与位置采用保守中文规则，复杂生活叙事通常先成为事件，需要人工整理才能变成准确的长期事实。

敏感正文、来源、向量、人脸特征、档案和提醒载荷用 Fernet；主题索引用 HMAC。SQLite 元数据仍可见，所以这是字段载荷加密而不是整库加密。Windows 密钥用 DPAPI 保护，其他平台采用受限权限文件；备份迁移需要同时管理数据库和密钥。跨机器、跨系统的迁移没有一键方案。

### 4.8 MBTI 和交流方式

用户可以自选 MBTI，以及 auto/listen/analyze/explore 支持方式。personality.py 和 conversation.py 将它们组织成沟通规则，当前表达优先于类型。

这属于交流冷启动与偏好设置，不是从摄像头推断 MBTI，也不是自动建立经过验证的人格数字孪生。明确反馈，例如“少问一些”，有单独处理和统计；不能据此宣传为完整人格学习。

### 4.9 陪护

CareService 是确定性服务层：相对时间提醒、到期确认、延后、重复、撤销、安静时段和明确启用的温和关怀。主动关怀默认关闭，默认安静时段 22 点到次日 8 点。提醒有 occurrence 校验，防止旧回执错确认下一次提醒。

安全文字分流会处理当前明确的危险表达、药物边界等，避开部分引用、否定和过去事件。它不是经验证的跌倒检测、医学诊断或自动报警器；回应明确表明没有代为拨号。

提醒依赖服务与接收端保持运行。这里没有证明机器人离线、电池耗尽或进程崩溃后仍能保证关键提醒送达。

### 4.10 机器人桥接

`robot.py` 定义 home-companion/1 输出协议，提供 capabilities、heartbeat、status 和 turn 路径。独立 `X-Robot-Token` 至少 24 字符；心跳超时 6 秒、急停或低电量会要求保持。

当前桥接硬编码 `motion_enabled=False`，运动 command=HOLD、authorized=False，只允许受状态控制的屏幕与声音输出。这是很清楚的输出接口边界，不能称已经接入机器人行走、机械臂或导航。V2 的模拟控制器和 V5 的实际输出协议需要分别看待。

## 5 Anima 用了什么以及训练证据

### 5.1 技术清单

Python 3.12 为原验证环境；主要依赖包括 PyTorch 2.6.0 CUDA 12.4、Transformers、PEFT、Accelerate、FastAPI、Uvicorn、Pydantic、NumPy、OpenCV、ONNX Runtime、MediaPipe、sherpa-onnx、faster-whisper、CTranslate2、edge-tts、cryptography、psutil 和 pytest。具体固定版本见 v5/requirements.lock.txt。

该 lock 文件是 Windows/CUDA 环境快照，包含 CUDA Torch 和平台相关依赖，不是可直接跨 macOS/ARM 安装的便携锁文件。当前 Mac 的系统 Python 是 3.9.6，无法直接按原说明复现完整环境。

主要数据来源：V2 使用 CPED、MASSIVE zh-CN、CrossWOZ；V4 增加 Chinese Multi-Emotion Dialogue Dataset、OpenS2S 文本、少量逐条审查 OASST2，以及自编家庭与修复场景。V5 语音专项记录 AISHELL-3、THCHS-30 噪声和一份粤语单说话人子集。存在下载或训练脚本不等于对应候选权重已发布或部署。

## 6 Anima 的交付缺口

1. **训练权重缺失。** Qwen 底座、V2 分类头、V4 当前状态与回复适配器、CPU 导出和 V5 感知模型都没有随 Git 提交。底座可从上游获得，但项目自训适配器没有公开下载包。
2. **原始证据缺失。** .gitignore 排除了大部分 reports、data、runs、models。提交的文字报告引用很多不存在的 JSON、日志、划分清单和上游快照。公开仓库能读结论，不能充分复核结论。
3. **下载流程有外部前置文件。** `download_social_encoders.py` 读取未提交的 `reports/upgrade_20261001/upstream/emotieff_tree.txt` 和 `sensevoice_onnx_api.txt` 取得固定 SHA；因此它不是仅凭新 clone 就能执行的完整模型准备器。
4. **依赖平台偏 Windows。** 启动脚本、DPAPI、摄像头适配和 CUDA 快照主要服务原电脑。存在部分 Linux 代码或 shell 入口，不等于 macOS、ARM 或机器人板卡已验证。
5. **文档版本不同步。** V5 README 的视觉、声音和上下文限制仍有旧说明；根 README 更接近当前主线。后续交付应统一支持矩阵。
6. **科研目标和发布范围分离。** 当前没有有效长期未来预测、多人关系图、因果干预评估或社会群体模拟。HumanState 是当前观察与统计，不能直接当成训练好的世界动力学模型。
7. **场景质量仍需建立。** 真实老人、儿童、嘈杂环境、跨天记忆、多人换人、误认、语音回声及长期使用效果缺少可交付的独立验收。
8. **系统架构仍有版本继承债务。** V5 通过 sys.path 导入 V4/V2，启动、测试与模型路径跨版本关联。作为研究演进合理，但整理成稳定 SDK 时需要明确包边界和兼容版本。

这些缺口意味着需要员工提供一次完整可验证交接。它们不证明员工没有训练过，也不证明报告虚假；它们证明现在这份 Git 仓库不足以让另一位工程师独立恢复完整系统。

## 8 看板的实时链路

```text
摄像头 JPEG 约每秒一张 + 麦克风 16kHz 单声道 PCM
  → 浏览器 WebSocket
  → 本机 Node.js/ws 桥接
  → 千问 Omni 同一个音视频会话
  → 云端 VAD 判定一句话结束
  → JSON 观察、听到原话、判断、决策建议
  → 页面展示与记录导出
```

默认模型为 `qwen3.5-omni-flash-realtime`。默认 server_vad threshold=0.5、静音 700 毫秒，页面可配置 300–2000 毫秒。模型会话 modalities=['text']，返回结构化文字，所以实时输入音频不等于已经有机器人语音输出。

heard 字段是模型对原声的回显，不是独立 ASR 服务的输出，也不再送给另一个推理模型。Realtime 默认情况下是一体化理解和决策，而不是“先千问视觉、再 DeepSeek 思考”。

桥接处理 session.update、音频 append、图像 append、speech_started/stopped、response.created、text.delta/done 和 response.done。音频先于图像，避免没有音频上下文就发图；配置或服务背景改变会关闭会话。前端处理新轮次使旧结果失效，顾客更换也重新建立会话。

服务最多接受两个实时连接，有载荷大小、上游连接超时、网络发送拥塞和错误处理。它并不等于成熟的多租户并发服务，没有分布式队列、集群状态或多机器人 fleet 管理。

导入带音轨视频走同一实时通道，文件上限 100MB；约一帧每秒是采样观察，不是连续逐帧视频理解。快速短暂动作可能遗漏，口型和语音来源也可能被模型误关联。

## 9 看板的图片链路

图片链路保留双阶段：`qwen3-vl-plus` 做可见场景和事件观察，然后 `qwen-plus` 或用户配置的 DeepSeek/custom 接口结合观察、面部系数、顾客表达及已授权备注给建议。

HTTP `/api/analyze` 使用 NDJSON 逐阶段发 start、stage、result、error 和 complete。模型原文、模型名、请求 ID、耗时和 usage 保留；JSON 不符合约定、输出截断或请求失败不会被换成假结果。

源码还保留 `/api/transcribe` 和 qwen3-asr-flash 兼容路径，属于旧式/独立实验接口，并不是当前实时视频对话中间必经的 ASR。模型配置中的“图片判断模型”也不能替换 Omni 实时模型。

所有决策标记 proposed。页面“思考摘要”只是可核对的摘要与依据，代码明确不声称提供模型内部思维链。

## 10 看板的顾客识别和记忆

Human 3.3.6 FaceRes 在独立浏览器 Worker 提取 1024 维特征。Worker 使用 WebGL；实际启用 blazeface、facemesh、faceres，禁用情绪、活体、防伪、身体、手部和物体等其他功能。Human 可以计算年龄/性别，但这里丢弃这些输出。

后端要求本次同意、单人、置信度至少 0.8、人脸尺寸至少 160、质量条件和有效 1024 维向量。默认匹配阈值 0.70，第一第二候选还需要至少 0.08 分差。超过或接近阈值但身份不清时返回 uncertain，而不是强行登记新身份。阈值可设 0.55–0.95；上限 250 个档案。

匹配使用 Human 对应的欧氏距离转换相似度公式，分数不是识别准确率。新顾客自动获得 C000001 等编号，称呼与服务备注由人编辑；可以关自动登记，只匹配已有档案。

持久化在 `data/service.json`：版本、模型、角色提示词、阈值、自登记设置、编号、人脸向量、称呼、备注、登记和最近见到时间。用串行队列、临时文件与 rename 降低并发覆盖风险，但它仍是单机 JSON 存储，没有数据库级大规模检索或多端同步。

识别结果产生约 60 秒的短期凭据，模型背景只加入该凭据对应顾客的编号、称呼和备注；不发送向量给千问。顾客未知、多人或换人会清空前一顾客上下文。

这里的“记住顾客”主要指固定档案和人工备注。没有自动从所有对话学习偏好、订单与交易历史，也没有跨门店统一 ID 或账户登录系统。人脸识别由本地浏览器提供特征，并不构成可信强身份验证。

与 Anima 的差别在于：看板是现场操作员得到同意后启用顾客识别；Anima 是成员先用 PIN 登录，再分别管理记忆和人脸许可。两个用户 ID、向量格式和权限逻辑不能直接互通。

## 11 看板的技术与数据边界

依赖只有三个主包：@mediapipe/tasks-vision 1.0.1、@vladmandic/human 3.3.6、ws 8.21.3。Human 自带相关模型工件，MediaPipe Face Landmarker 由 setup 下载。项目没有训练 Omni、没有独立训练“机器人大脑”，主要是组合预训练模型和云 API。

服务默认监听 127.0.0.1:4173；HTTP 与 WebSocket 检查 Host 和 Origin，静态文件解析路径及真实路径都限制在 dist 目录。API Key 默认进程内存，不写浏览器存储或导出记录；可选 .env 持久化，代码从项目 .env 读取。

原始声音和采样画面持续发往配置的千问服务。顾客向量留本机，但称呼和服务备注进入云端模型提示词；向量不出网不等于所有个人资料都不出网。

本机档案文件未加密，不包含照片，但向量仍是身份特征。当前系统按单机操作员信任边界设计，不应直接改监听地址部署成公网 SaaS。

最近四张发送帧、输入时段、原文、响应 ID 和 usage 可导出；没有完整录像和原始音频长期保存，因此调试可核对性优于纯截图，但不足以做完整标注数据回放。

## 14 两者如何组合

可以复用的是能力和工程结构：Anima 的 HumanState、时序线索、记忆与个人偏好；看板的原声音视频链路、可见场景理解、结构化展示和来源记录。

主要冲突如下：

| 冲突 | 当前情况 | 若整合需要做什么 |
| --- | --- | --- |
| 输入 | Anima 结构化线索；看板原始音视频 | 定义 SensorFrame 与 ObservedEvidence，不丢时间和来源 |
| 模型 | 本地短句 Qwen；云端 Omni | 用独立后端适配层，保持同一输出协议 |
| 身份 | PIN成员/SFace；现场顾客/Human | 统一 Person ID 与授权；不同 embedding 不能混算 |
| 记忆 | 加密SQLite多层记忆；明文JSON备注 | 统一存储和撤回语义，保留本地/云端许可区别 |
| 状态 | HumanState 连续统计；单轮事件 JSON | 区分当前观察、历史状态与模型推断 |
| 动作 | HOLD输出协议；自然语言建议 | 统一 ActionProposal，真实执行交给厂商控制器 |
| UI | 家庭成员试用；技术团队实验 | 分别保留用户界面和工程看板，不能混成一个复杂首页 |
| 评测 | 公共/合成回放；协议/云端演示 | 用同一批场景、同一指标和完整输入回放比较 |

合理的目标结构是“感知与输入 → 人与会话状态 → 记忆及场景规则 → 决策建议 → 控制器授权 → 真实执行回执 → 状态与质量评测”。目前两个项目覆盖了前半段，真实控制和反馈闭环仍缺。

本地与云端选择不能只看参数大小。应在同一测试集记录延迟、成本、可离线程度、ASR 错误、物体/事件遗漏、记忆正确性、身份串线和决策质量。云端可先作为研发比较对象，但两者当前没有完成 teacher 蒸馏或自动数据闭环。

**Anima 有较多实质工程与训练资产线索，超出简单套壳网页；看板有真实链路、结果校验和上下文管理，超出静态可视化演示。** 两者都谨慎记录了许多能力边界，代码也存在相应限制。

## 17 优先推进顺序

先恢复 Anima 的模型与原始证据包，使新电脑可以重复原结果；同步整理 Windows/CUDA 与其他平台支持矩阵。然后统一输出契约和场景评测，保留两个前端用途。再接一台真实机器人，先完成屏幕/语音输出和停止机制，再逐项加入受控动作。

评测应至少包括：同一成员跨天事实纠正与遗忘；陌生人/多人/换人不串档案；文字与表情冲突时尊重自述；弱光与噪声下拒识/重问；快速事件采样遗漏；提醒重复回执；断网、重连和进程重启；建议动作与真实执行状态严格区分。只有这些链路可靠以后，再讨论训练社会状态转移与反事实预测。
